# ПРОИЗВОДИТЕЛЬНОСТЬ — замеры, бюджеты, как проверять

Обновлено: 2026-10-30. Всё измеряется скриптами из `tests/audit/`, а не «на глаз».

## Как запустить

```bash
# прод-сборка + SPA-fallback + прокси /api → backend
node tests/audit/serve.cjs 5590

node tests/audit/run.cjs   http://localhost:5590   # аудит: консоль, вёрстка, тач-цели
node tests/audit/e2e.cjs   http://localhost:5590   # сквозной проход по сценариям
node tests/audit/bench.cjs http://localhost:5590   # бенчмарк кадров (медианы)
node tests/audit/bench.cjs http://localhost:5590 --check   # сравнение с baseline.json
node tests/audit/bench.cjs http://localhost:5590 --save    # новый baseline
```

`--check` падает, если метрика стала хуже baseline более чем в **2.5×** — это защита от
регрессий, а не от шума конкретной машины.

> Важно про замеры: цифры сильно зависят от загрузки сервера и от того, аппаратный ли
> растеризатор в браузере. На этом сервере `load average` бывает 10+ на 4 ядра — в такие
> моменты любой кадр «дорожает» в 2–4 раза. Бенчмарк берёт медиану из 5 серий, baseline
> снят при load ≈ 7.

## Текущие числа (медиана, dist-сборка)

| Метрика | Что это | ms/кадр |
|---|---|---|
| `papercast-600x900` | один персонаж PaperCast, 600×900, смена позы + seek | **2.1** |
| `animals-dog` | животное (пёс) на 600×900 | **0.3** |
| `stage-2-actors` | PaperCastStage: комната, 2 актёра, субтитры | **9–15** |
| `scene-seek-p50` | полный round-trip `__sceneSeek` в iframe сцены `/p/12` | **13–17** |

Бюджет: сцена на 60 fps требует < 16.7 мс/кадр; двухактёрная сцена укладывается, один
персонаж имеет 7-кратный запас. Рендер видео (1920×1080, offscreen) — ~35–50 мс/кадр,
то есть минутный ролик рисуется 1–2 минуты.

## Что уже оптимизировано

1. **Контактная тень** — была `ctx.filter = 'blur(4px)'` на каждом кадре, стала
   запечённым спрайтом с радиальным градиентом (`shadowSprite()`): −0.04 мс на кадр,
   плюс исчез целый класс медленных путей в растеризаторе (фильтры на больших канвасах).
2. **Бюджет пикселей** (`PIXEL_BUDGET = 1.4e6`): канвас с supersampling (dpr > 1)
   ограничивается 1.4 Мпикс. Телефон с dpr 3 больше не рисует 4 Мпикс на кадр. Канвас
   рендера видео (dpr 1, 1920×1080) не масштабируется — качество экспорта не страдает.
3. **Акторы сцены рисуются в свой реальный размер**: `PaperCast.setSize(w, h)` +
   `PaperCastStage` ставит каждому актёру канвас под его экранный размер (было
   600×900 → блит в 300 px, стало ~323×485 без пересэмплинга). Профиль показал, что
   `drawImage` занимал **77 %** времени кадра двухактёрной сцены.
4. **Никакого `requestAnimationFrame` внутри рига**: студии сами решают, когда рисовать;
   в фоновой вкладке не рисуется ничего (проверено: 600 мс простоя — 0 кадров).

## Аудит вёрстки (что проверяется автоматически)

- нет ошибок в консоли и упавших запросов на 9 страницах;
- нет горизонтального скролла на 1440×900, 1280×800, 390×844, 360×740, 844×390;
- тач-цели ≥ 24×24 px (WCAG 2.5.8 AA); «тесно» (24–32 px) собирается отдельным списком;
- нет текста меньше 10 px;
- inline-ссылки в предложении из проверки исключены (исключение WCAG).

Результат последнего прогона: **0 проблем** (`tests/audit/report.json`).

## Что осталось в бэклоге

- Кэш статичных слоёв PaperCast (торс/фон меняются реже головы) — потенциально ещё −30 %
  на кадр, но требует аккуратной инвалидации по позе/одежде.
- Разделение `drawShoe`/`drawHead` по слоям (сейчас ~25 % времени каждый) — оптимизация
  путей, а не архитектуры.
- Замеры на реальном телефоне (сейчас — эмуляция Chromium с software-растеризацией).
