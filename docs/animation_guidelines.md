# Руководство по созданию анимаций для видео-рендера

При создании новых компонентов Vue для нашего генератора презентаций **крайне важно** соблюдать определенные правила анимации. 
Движок рендера (`render_video.py`) использует `Playwright` и его `Virtual Time Policy`. Это значит, что скрипт ставит виртуальное время браузера на паузу, чтобы успеть сделать скриншот каждого кадра. 
Если анимации написаны неправильно, на экспортированном видео они будут "дергаться", проскакивать кадры или работать с огромной скоростью.

## ❌ Как НЕ НАДО делать (Ошибки)

### 1. Использование `requestAnimationFrame`
Обычный `requestAnimationFrame` с привязкой к `performance.now()` не работает корректно при паузах виртуального времени Playwright. Вызовы будут накапливаться или пропускаться, и анимация будет выглядеть как слайдшоу (резкая смена кадров).
```javascript
// ❌ НЕПРАВИЛЬНО
const animate = () => {
  const time = performance.now()
  // ... вычисление ...
  requestAnimationFrame(animate)
}
```

### 2. СТРОГО ЗАПРЕЩЕНО: Бесконечные CSS и SVG анимации (`infinite`)
Любые свойства `animation: ... infinite` в CSS (например, `class="animated-flow"`) или теги `<animateMotion>`, `<animate>` в SVG **категорически запрещены** для элементов, которые должны двигаться или переливаться. Они рассинхронизируются с виртуальным временем браузера при рендере Playwright. Из-за этого на видео вы получите эффект "бешеных линий", проскакивающие кадры или анимацию "как угорелую".

```html
<!-- ❌ СТРОГО ЗАПРЕЩЕНО (Бешеные линии при рендере) -->
<path class="animated-flow" />

<style>
  .animated-flow { 
    stroke-dasharray: 10 30;
    animation: flow-run 2s linear infinite; /* ЗЛО ДЛЯ РЕНДЕРА */
  }
</style>

<!-- ❌ СТРОГО ЗАПРЕЩЕНО (Неконтролируемые частицы) -->
<circle r="4">
  <animateMotion dur="2s" repeatCount="indefinite" />
</circle>
```

### 3. CSS Transitions на свойствах, обновляемых каждый кадр
Если вы вычисляете координаты JS-ом каждый кадр, не вешайте на этот элемент класс `transition-all`. CSS-переход попытается сгладить математически точный шаг, что приведет к конфликтам расчета времени в Playwright и заметным подергиваниям.

## ✅ Как ПРАВИЛЬНО делать (Паттерны)

Все анимации (особенно непрерывные) должны быть строго детерминированы и привязаны к инжектируемому значению `relativeTime`. Это глобальное время текущего слайда в миллисекундах.

### Паттерн 1: Вычисляемые стили (Computed / Inline Styles) для зацикленных анимаций
Если элемент должен постоянно двигаться (например, эффект пульсации, плавания или бегущей точки), просто вычисляйте его параметры прямо в шаблоне на основе `relativeTime` с помощью математики (`Math.sin`, деление по модулю и т.д.):

```vue
<!-- ✅ ПРАВИЛЬНО: Плавающая анимация -->
<div :style="{ transform: `translateY(${ Math.sin((relativeTime / 2000) * Math.PI * 2) * -10 }px)` }">
  Контент
</div>

<!-- ✅ ПРАВИЛЬНО: Бесконечный прогресс (от 0 до 100% за 2 секунды) -->
<div :style="{ left: `${ (relativeTime % 2000) / 2000 * 100 }%` }"></div>
```

### Паттерн 2: Реактивный переход между состояниями (Вместо rAF)
Если вам нужно анимировать переход от точки А к точке Б по триггеру (например, смещение камеры), используйте функцию-наблюдатель `watch(relativeTime)` и храните состояние анимации.

```javascript
// ✅ ПРАВИЛЬНО
import { ref, inject, watch } from 'vue'

const relativeTime = inject('relativeTime', ref(0))
let animationState = ref(null)

const triggerAnimation = (targetValue, duration = 1000) => {
  animationState.value = {
    startVal: currentValue.value,
    targetVal: targetValue,
    duration,
    startTime: relativeTime.value
  }
}

watch(relativeTime, (time) => {
  if (animationState.value) {
    const { startVal, targetVal, duration, startTime } = animationState.value
    const progress = Math.min((time - startTime) / duration, 1)
    
    // Применяем Easing (например, easeOutQuad)
    const ease = 1 - (1 - progress) * (1 - progress) 
    
    currentValue.value = startVal + (targetVal - startVal) * ease
    
    if (progress >= 1) {
      animationState.value = null // Анимация завершена
    }
  }
})
```

### Паттерн 3: Простые CSS Transitions (Одноразовые события)
Обычные CSS-классы с транзишенами (`transition-opacity duration-500`) **можно и нужно использовать**, если это простое переключение состояния (например, появление элемента).
Браузер Playwright корректно отрабатывает одноразовый переход во время виртуального времени.

```vue
<!-- ✅ ПРАВИЛЬНО (Для простых появлений/исчезновений) -->
<script setup>
const isVisible = computed(() => relativeTime.value >= 1500)
</script>

<template>
  <div class="transition-opacity duration-500" :class="isVisible ? 'opacity-100' : 'opacity-0'">
    Появляющийся текст
  </div>
</template>
```

### Паттерн 4: Разряженные тайминги появления айтемов

Появление каждого айтема — это анимация (transition 300–800 мс: fade/slide/scale).
Чтобы она успела **плавно проиграться**, `start_time` соседних айтемов расставляй
**разряженно**:

- Шаг между соседними айтемами — **≥ 800–1000 мс (рекомендовано ~1000+)**.
- После последнего айтема — **≥ 2000 мс** до конца слайда (воздух перед переходом).
- Плотная набивка (шаг 200–500 мс) = **рваный резкий эффект**: анимации не успевают
  отыграть, наслаиваются друг на друга, кадр дёргается.

```js
// ❌ ПЛОТНО — рваный эффект (анимации наслаиваются)
nodes: [{ start_time: 500 }, { start_time: 900 }, { start_time: 1200 }]

// ✅ РАЗРЯЖЕННО — каждая анимация успевает проиграться
nodes: [{ start_time: 500 }, { start_time: 1600 }, { start_time: 2700 }]
```

⚠️ Валидатор (`POST /components/{slug}/validate`) проверяет только **монотонность**
`start_time`, но **не плотность**. Плотность — дисциплина агента, автоматика её не ловит.

### Исключение: `InteractiveArchitecture` (канвас-схема)

На этот компонент правила плотности **не распространяются вообще**. У него своя
механика воспроизведения, и назначение таймингов всем айтемам ей **губительно**:

- `start_time` ставится **только у ОДНОЙ ноды** — это фокус камеры, а не «появление».
- Остальные ноды **без `start_time`** — появляются автоматически по мере облёта камеры.
- НЕ задавай `x`/`y` — раскладка строится топологическим BFS автоматически.
- Если `start_time` у всех нод → камера мечется между фокусами, схема «колбасит».

```js
// ✅ Правильно для InteractiveArchitecture: один start_time = фокус камеры
nodes: [
  { id: 'n1', label: 'X', start_time: 0 },  // фокус камеры
  { id: 'n2', label: 'Y' },                  // появится автоматически
  { id: 'n3', label: 'Z' },                  // появится автоматически
]
```

### Резюме:
- **Никаких `requestAnimationFrame`** в компонентах.
- **Никаких `<animate>` в SVG**.
- **Бесконечные анимации** = `Math.sin(relativeTime)`.
- **Сложные переходы (JS)** = `watch(relativeTime)`.
- **Простые появления** = `transition` + `relativeTime >= threshold`.
- **Тайминги айтемов** = разряженно (шаг ≥ 800–1000 мс), кроме `InteractiveArchitecture`
  (там `start_time` только у одной ноды).

## Render-friendly анимации (realtime-захват)

Серверный рендер — realtime-захват (`ffmpeg x11grab`), но Chromium запускается с
`--disable-gpu` (софтверная растеризация). Поэтому стоимость отрисовки **одного
отображаемого кадра** на CPU определяет, удержит ли браузер 60 fps; перегруз → дроп
кадров в mp4. `backdrop-filter` в render-режиме отключён осознанно (`main.js`, ещё с
первого коммита) — из-за дороговизны в софте.

Правило: **непрерывные** (весь слайд) анимации — только `transform`/`opacity`.
Прогресс линий/баров двигать через `transform: scaleX/scaleY` (с `transform-origin`),
а не `width`/`height`; «бегущий» блик — `transform`, а не `background-position`.
Однокадровые «проявления» (grow/появление один раз) — как удобно, они краткие.
`filter: blur` / `feGaussianBlur` не запрещены (решение владельца), но если конкретный
слайд тормозит в рендере — начинать диагностику с них.

Исправлено (непрерывные анимации): `PortraitLampSlide` (background-position → transform),
`TimelineSlide` и `Roadmap` (width/height → scaleX/scaleY).
